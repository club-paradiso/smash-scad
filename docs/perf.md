# 성능 측정 기록

측정일 2026-11-20. 원자료는 `docs/perf-data/*.json`(시나리오별 3회 반복 원값과 중앙값)에 있다.

## 먼저 읽을 것: 이 숫자가 뜻하는 것과 뜻하지 않는 것

- 전부 **GPU가 없는 컨테이너의 헤드리스 Chromium**에서 쟀다. WebGL은 SwiftShader(CPU로 돌리는 소프트웨어 렌더러)다. FPS는 6~12 수준인데, 이건 **실기기 성능이 아니다**. 실제 GPU에서는 래스터와 정점 셰이딩 비용이 훨씬 작아서 비율도 달라진다.
- 그래서 판단은 FPS보다 다음 지표를 우선으로 했다.
  - 그린 삼각형 수, draw call 수: 기기와 무관한 값
  - 탭 레이캐스트 시간, 지오메트리 생성 시간: 메인 스레드 JS라 실기기에서도 같은 방향으로 나타난다(폰 CPU는 이보다 느림)
  - 프레임당 업로드 바이트: `tools/perf/upload_ranges.mjs`로 계산한 결정적 값
- iPhone Safari, Android Chrome, 실제 GPU 데스크톱에서는 **측정하지 않았다**(미검증).

## 환경

| 항목 | 값 |
|---|---|
| 브라우저 | Chromium 157.0.8103.78, Playwright 헤드리스 |
| WebGL | ANGLE (Google, Vulkan 1.3.0 (SwiftShader Device (Subzero)), SwiftShader driver), WebGL 2.0 |
| GPU | 없음 (SwiftShader 소프트웨어 렌더링) |
| 기기 | Linux 컨테이너, vCPU 4개, RAM 15GB |
| 화면 | 1280×800, deviceScaleFactor 1 |
| 서버 | r147: `python3 -m http.server`(원본 `web/`), 이후: `vite preview`(`dist/`) 또는 같은 빌드를 `python3 -m http.server`로 |
| 반복 | 시나리오마다 새 페이지로 3회, 표는 중앙값 |

r147 원본은 three.js를 jsDelivr CDN에서 받는데, 이 컨테이너의 네트워크 정책이 jsDelivr를 막는다(403). 그래서 측정할 때만 Playwright가 같은 URL 요청을 npm `three@0.147.0` 패키지의 같은 파일(`build/three.min.js`, `examples/js/controls/OrbitControls.js`)로 응답하게 했다(`--cdn` 옵션). 게임 코드는 바꾸지 않았다.

## 측정 방법

주소에 `?perf`를 붙이면 `window.__smash` 훅이 켜진다. 없으면 게임 동작은 같다. 측정 스크립트는 `tools/perf/measure.mjs`.

| 항목 | 방법 |
|---|---|
| 데이터 fetch | `fetch('scad-savannah.json')` 시작부터 JSON 파싱 끝까지 (1.0MB, 로컬 서버) |
| 지오메트리 생성 | `buildCity()` 전체: 건물 4,497개 지붕·벽 생성, 버퍼 병합, 법선, 색 칠하기, (적용 후) BVH 생성과 타일 메시 생성 포함 |
| BVH 생성 | 위 시간 중 `new MeshBVH()`만 따로 |
| 첫 렌더 | 지오메트리 생성 끝부터 첫 `render()` 뒤 `readPixels`로 GPU 완료를 기다린 시점까지 (셰이더 컴파일 포함) |
| 로드 합계 | 페이지 탐색 시작(performance.now 0)부터 첫 렌더 완료까지 |
| 평상시 FPS | 시작 버튼 누르고 1.5초 뒤 5초 동안 rAF 프레임 수. 기본 시점(Downtown) |
| 핵 직후 FPS | 기본 시점 중심에 핵 발사, 살아 있는 건물 수가 줄어든 프레임부터 4초 |
| 지진 중 FPS | 기본 시점 중심에 지진, 발동 직후부터 4초 |
| render() ms | 프레임마다 `renderer.render()` 호출의 메인 스레드 시간. GPU 프로세스 쪽 시간은 안 들어간다 |
| 탭 레이캐스트 | 화면을 20×10 격자로 나눈 200지점에서 탭 판정 함수(`pickAt`)만 실행한 시간. 브라우저 타이머 해상도가 0.1ms라 0.1ms 미만은 0으로 찍힌다 |
| 업로드 벤치 | 매 프레임 건물 N개를 다시 dirty로 만들고, 도시 메시는 삼각형 1개만 그리게 한 뒤 128×80 캔버스에 렌더하고 `readPixels`로 동기화한 시간. 정점 셰이딩과 래스터 비용을 거의 없애서 속성 업로드 비용만 남긴다. 30프레임 중앙값 |

참고: 게임 시간은 프레임당 최대 0.05초로 잘린다. SwiftShader처럼 느린 환경에서는 같은 4초 동안 진행되는 게임 시간이 FPS에 따라 달라서, 지진으로 무너진 건물 수(61~174)가 빌드마다 다르다.

## 업로드 비용

### 업로드 벤치 (SwiftShader, 128×80, 동기화한 프레임 시간, ms)

| 프레임에서 바뀐 건물 | r147 원본 | Vite + r187 | + 범위 업로드 | 공간 재배치 추가 (기각) | 최종 |
|---|---:|---:|---:|---:|---:|
| 없음 (기준) | 9.2 | 9.2 | 9.1 | 8.7 | 9.3 |
| 1개 (폭탄 1발) | 10.9 | 11.2 | **9.2** | 9.3 | 9.0 |
| 목표 주변 200개 (핵과 비슷) | 10.9 | 11.4 | **9.6** | 9.2 | 9.8 |
| 흩어진 200개 (최악) | 11.2 | 11.2 | 10.9 | 11.2 | 11.6 |
| 4,497개 전부 (복구 버튼) | 12.2 | 11.5 | 11.1 | 12.3 | 12.7 |

전체 업로드는 이 환경에서 프레임당 약 2ms다. 범위 업로드로 건물 1개, 근처 200개일 때 그 2ms가 거의 사라진다. 흩어진 200개와 전체는 전체 업로드로 넘어가므로 그대로다(설계대로).

### 프레임당 업로드 바이트 (결정적 계산, `node tools/perf/upload_ranges.mjs`)

기본 시점 목표(Downtown) 기준, 속성 하나(aL 또는 color)당 값이다. 손상이 있는 프레임에는 두 속성이 다 올라갈 수 있다.

| 무기 (반경) | 맞는 건물 | 이전 (전체 업로드) | 범위 업로드, OSM 순서 | 최종 (타일 순서) |
|---|---:|---:|---:|---:|
| 폭탄 (30m) | 1 | 4,053 KB | 1개 범위, 1 KB | 1개 범위, 1 KB |
| 운석 (85m) | 18 | 4,053 KB | 6개 범위, 27 KB | 3개 범위, 30 KB |

무너지는 건물은 붕괴 애니메이션(0.8~1.4초) 동안 매 프레임 aL이 바뀐다. 이전에는 그동안 매 프레임 4MB씩 올렸고, 지금은 핵 기준 181KB다. 실기기 메모리 대역폭에서 의미 있는 차이일 가능성이 높지만, 실기기에서 FPS로 확인하지는 않았다.

| └ 타일 분할 + 절두체 컬링 (LOD를 위해 넣은 기반) | 단일 메시는 바운딩 구가 도시 전체라 컬링이 안 됐다. 400m 타일 54개로 나누니 기본 시점 삼각형 134,513 → 47,783(−64%), draw call 5 → 22, FPS 9.6 → 12.0(SwiftShader). 최대 줌아웃에서는 134,513 → 98,746. 로드 시간 차이는 노이즈 범위(지오메트리 생성 192 → 191ms) | **채택** (단독으로 효과가 측정됨) |

타일 컬링의 FPS 이득은 SwiftShader가 정점 처리에 약해서 크게 나온 것이다. 실제 GPU에서는 34만 정점이 원래 부담이 아니라 이득이 훨씬 작을 수 있고, draw call이 5 → 22개로 늘어난 비용(작음)과 맞바꾼 것이다. 실기기 측정 전까지는 "삼각형 수 −64%"만 확정 사실이다.

- 레이어별로 꺼 보면(1280×800) 지면 전체를 끌 때 FPS 8.8 → 11.3, 나무를 끌 때 8.8 → 10.0이다. 지면 쪽은 겹친 평면을 SwiftShader가 픽셀 단위로 그리는 비용이 대부분이라 실제 GPU에서는 훨씬 작을 것으로 보지만 측정하지 않았다.
- 업로드 벤치는 이번 버전부터 비교할 수 없다. 벤치는 도시 메시만 삼각형 1개로 줄이는데, 지면과 나무는 그대로 그려져 기준값 자체가 커졌다(9 → 26ms).
- 휴대폰 에뮬레이션(iPhone 13, 기기 픽셀 비율 3)에서는 해상도 자동 조절이 픽셀 비율을 2로 시작해, SwiftShader 프레임이 41ms로 느리자 1까지 내렸다(`tests/e2e/mobile.mjs`). 실기기에서 어디까지 내려가는지는 미검증이다.

| 평상시 그린 삼각형 | 81,752 | 85,526 | 85,526 (+그림자 패스) |
| 평상시 FPS (SwiftShader) | 7.8 | 7.0 | 3.5 |
| 핵 직후 FPS (SwiftShader) | 5.6 | 5.2 | 2.8 |
| 데이터 파일 | 1.93MB | 2.37MB (gzip 787KB) | 같음 |

- 그림자는 SwiftShader에서 FPS를 절반으로 만든다. 실제 GPU 비용은 측정하지 않았다. 그래서 휴대폰은 기본 끔, 데스크톱은 켜되 프레임이 계속 느리면 자동으로 끈다(이 환경에서는 몇 초 뒤 꺼진다).
- 실측 형태를 SCAD 외 건물로 넓히면서 처음에는 지붕 삼각형이 31만 개였다. 평평한 지붕은 상자로 두고, 거친 맞춤과 맞지 않는 건물은 상자로 되돌려 5.7만 개로 줄였다.

## 다시 재는 법

```bash
npm install && npm run build
npm run preview &                                   # http://localhost:8765
npm run perf -- --label mine --runs 3               # docs/perf-data/mine.json
node tools/perf/measure.mjs --url http://localhost:8765/ --label mine-upload --only upload
node tools/perf/upload_ranges.mjs                   # 업로드 범위·바이트 계산
node tools/perf/lod_stats.mjs                       # 건물 크기별 정점 비중
node tools/perf/shots.mjs --url http://localhost:8765/ --out shots   # 비교용 캡처
node tools/perf/measure.mjs --url http://localhost:8765/ --label phone --w 390 --h 844   # 휴대폰 크기
```

실기기에서 재려면 같은 빌드를 휴대폰에서 열고 주소에 `?perf`를 붙인 뒤, 원격 디버깅 콘솔에서 `__smash.rec(true)`, 몇 초 뒤 `__smash.rec(false); __smash.FR`로 프레임 로그를, `__smash.PT`로 로드 시점을 읽으면 된다.
